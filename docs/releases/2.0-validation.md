# ClayFighter 64 2.0 validation record

Own work: **djultra64**. Status on **2026-10-14: local v2.0 release validated**.
Results apply to the builds and scenarios below. They do not certify every
character animation, controller or hardware configuration.

## Frozen builds and native checks

The current build passed **45 Linux native checks** (44 suite checks plus the
separate dispatch check) and **60/60 Windows native checks**. The final Windows
suite completed in 5.63 seconds. Windows GPU checks used an RTX 2060 with the
native Original 60 Hz target. Real Xbox, PlayStation and Nintendo Switch
controller verification remains pending when that hardware is available.

The integration owner recorded all 64 authentic Claytality variants passing
native eligibility checks with **256 positive and 712 negative cases**. The
input matcher passed **384 positive and 160 negative cases**, including both
sides and different durations. Those fixtures stub animation execution;
passing them does not prove all 64 finisher animations play successfully.
A full Linux Frosty practice run observed phase 8 followed by phase 7 and
successful fast restart. Other native and runtime checks cover Training
selection, stage Back, pause/navigation, resources, positioning, Main Menu,
and Change Fighters & Stage within their recorded scenarios.

## Long runtime and restart checks

A **1,901.4-second Linux Normal Training run** ended with exit 0 and no stall.
Its continuous sample record contained 1,520 phase-3 observations, ticks 755
through 91,860, the same world/session, timer 99, HP 170, and pause/attract flags
0. Memory observations covered 118 samples: startup compilation/cache use
reached approximately 613 MB, then settled around 149 MB. The final process
had 83 threads and constant virtual size of 4,634,084 KB. This Normal run
preceded the final fast-restart and window-label changes; its unchanged Normal
rules are the scope of that evidence.

The **final Linux manual restart stress test** ran for 601.2 seconds and ended
with exit 0 and no stall. It delivered 100 scripted logical restart presses,
recorded 100 native scene shutdown/ready transitions and 101 combat loads
with the same Frosty/Blob selections. The final timer remained 99 and both
fighters had full health. Restarts use reviewed native cleanup and skip the
intro. Measured control delay (press interval minus 500 ms) was 1,820 ms
minimum, 1,974 ms median and 3,654 ms maximum under parallel llvmpipe runs.
The observed result is approximately two seconds; the one-second target has
not been fully achieved.

The **final Windows Claytality stress test** completed its 1,300-second bounded
run with process exit 0, no timeout, no error and a non-stalled validation event
(76,918 graphics tasks and 151,964 input polls). Retained native state traces
verify **100 complete phase-8 to phase-7 Frosty finishers**, 108 combat entries
and 107 native repeats. The seven additional repeats exercised expired practice
windows after the scripted inputs finished. All combat entries retained the
chosen Frosty/Bonker matchup and reinitialized Training. The application ended
naturally at its configured deadline.

Windows resource sampling recorded 24 observations during the final 11.5 minutes:
private memory increased from 589,959,168 to 610,254,848 bytes and working set from
436,285,440 to 457,400,320 bytes. A targeted review found no new unbounded
Training-owned container, but did not identify the cause or prove a plateau.
**Longer Windows memory stability remains a validation limitation**; no claim of
constant Windows resource use is made.

## Clean installation and portable candidates

Fresh candidates in `local/releases/2.0-candidate/` contain the final fast
restart implementation. Both platforms passed actual two-ROM installation
with the packaged importer and checksum parity for the three generated game
files. Each installation was moved into a path containing spaces. A
20-second packaged-launcher boot with the Original graphics profile and
scripted startup input then completed with launcher/native exit 0, no stall
and no timeout. Windows used bundled Python, release DLLs and its actual GPU;
Linux used private Xvfb and software Vulkan. These are startup checks,
separate from the repeated-session tests above.

The successful Linux run left its redirected HOME/XDG canary outside the
installation completely empty. Windows startup establishes execution and
import parity; this check did not independently monitor every external
Windows profile write. Real controller action/prompt checks remain pending.

Candidate manifests verified **932 Linux files and 975 Windows files**, all
per-file hashes and archive SHA-256 values, with no ROM imports or saved
settings in the public payload. The authored source preserved the authentic
zstd `build/LICENSE` notice. Candidate archive hashes and inventories apply to
that snapshot; final source/doc changes require fresh final archives.

Earlier provisional packages in `local/releases/2.0-validation-staging/` also
passed clean import and moved-folder startup checks. An initial Linux boot
with the default presentation profile and no startup input reported a stall;
its retained log is not counted as a successful run. The successful Original
profile startup checks above do not erase that earlier observation.

## Packaging and exact dependency sources

The following current checks completed successfully:

```sh
python3 -m unittest tests.public_release_test tests.release_package_test tests.release_import_test
python3 -m py_compile tools/release/package.py tools/release/sdk_source.py tools/release/public_files.py
git diff --check
```

The **11 unittest checks** cover safe version names, Linux/Windows assembly
with stub binaries, source exclusions, authentic notices, manifests/checksums,
ROM header/suffix rejection, symlinks and portable path escapes, ROM byte-order
and ZIP handling, and actual two-ROM extraction parity. Incorrect, duplicate
and single-ROM inputs are rejected before persistent import. Stub assembly
checks establish packaging behavior; the actual packaged startup checks are
recorded separately above.

All **10,125 vendor files** in the prepared SDK inventory match the actual
`deps/` tree by SHA-256, without missing or modified files. Authorized Windows
source checks matched **8,439 RT64 files and 911 runtime files**, including the
same detached Git commits. Their extra upstream files contain no additional
CPP/C/H/HPP/Python/CMake implementation files beyond the prepared inventory.
Installed Linux receipts confirm SDL2-compat 2.32.70, SDL3 3.4.12 and dbus
1.16.2. Windows uses native SDL2 2.26.3; its installer includes CPython 3.13.9.

The Linux RT64 build-local copy matches 8,439 pinned source files except its
CMakeLists, whose repair hash matches `RT64-SOURCE-PATCH.json`. The archived
SDK preserves the original CMakeLists. SDK filter fixtures retain required
spimdisasm `analysis/` implementation code and exclude Git metadata, CMake
outputs and ROM suffixes.

The prepared Windows SDL2 tree contains headers/build inputs without its C
implementation. The official [SDL2 2.26.3 source
archive](https://www.libsdl.org/release/SDL2-2.26.3.tar.gz) was added locally;
its version header, implementation and authentic license were verified.
Its SHA-256 is
`c661205a553b7d252425f4b751ff13209e5e020b876bbfa1598494af61790057`.
The shipped SDL2.dll also matches the x64 DLL in the official
[SDL2 2.26.3 Visual C++ development
archive](https://www.libsdl.org/release/SDL2-devel-2.26.3-VC.zip) byte for byte.
The SDK recipe includes native Windows SDL source alongside the separate
Linux source archives, checks their recorded hashes, and preserves dependency
notices under `sdk/licenses/`, including notices for prebuilt DXC inputs.
The original prepared dependency trees were not modified.

## Final archives

The versioned Linux, Windows, authored-source and prepared-SDK source archives
are generated under `local/releases/2.0/`. `SHA256SUMS` records archive hashes;
binary-package manifests record per-file hashes. Matching SDK sources include
Windows SDL2 2.26.3 and preserved dependency notices. ROMs, extracted cartridge
assets, private translations and user settings are excluded. The final archive
inventories and checksums are verified after creation.

No exhaustive finisher-animation or physical-controller coverage is inferred
from fixture counts. Historical [1.0 results](../VALIDATION_1.0.md) remain scoped
to that release.
